# V49 知识库绑定数量边界统一接口包说明

## 目标与范围

修复 V0.1 Release Gate 的 P2-01：绑定写入允许 50 个而执行最多接受 20 个。生产基线为已封版 `v0.1` / `1d062df`。本片统一知识库绑定写入、新任务快照和 RAG 执行上限为 20，不提高运行时资源上限。

## 接口与数据契约

- `PUT /api/v1/agents/{id}/knowledge-bases`：原始 `knowledgeBaseIds` 数组最多 20 项；超过限制返回 400/`COMMON_PARAM_INVALID`，不改变既有绑定。继续使用原有去重、排序和 owner 隔离语义。
- `GET /api/v1/agents/{id}/knowledge-bases`：完整保留已有绑定，前端继续兼容读取最多 50 项；这是历史数据修复入口，不表示仍允许写入 50 项。
- 新任务创建在冻结快照前检查已有绑定总数（包括当前不活跃或已软删知识库的残留绑定）。超过 20 返回 409/`AGENT_BINDING_INVALID`，不新增 task/event，不调度，不调用模型、embedding 或工具。
- 已有 task 的 GET/Trace、相同 key 的合法幂等复用不受当前绑定配置变化影响。历史超限绑定由用户明确删减并全量保存，不自动截断或迁移。
- 运行期继续使用同一个后端数量常量做防御校验；不截断已冻结的 snapshot，不将旧超限 snapshot 自动重写为其他输入。
- 前端显示 `已选 N / 20`，超限时仍可移除已选项；新增选择及保存受限制。保存前拒绝不进入未知写入状态，原有独立保存与未知结果 GET 核对保持不变。

## 明确不做

不增加业务 API、数据库迁移、任务恢复、执行重试、新工具、多知识库检索质量评测或动态限制配置；不回写/重打 `v0.1` tag。20 个可绑定仅是数量契约，不能替代 READY、owner、profile 或模型预算检查。

## 面试问题与回答

**问题 1：为什么将写入降到 20，而不把执行上限提高到 50？**

回答：20 是当前已有的运行时资源边界。提高到 50 会扩大快照和检索规模，本片只解决契约不一致，不在缺少相应容量证据时扩容。

**问题 2：写入最多 20，为什么 GET 仍可返回历史 21–50 个？**

回答：历史配置必须完整可见才能修复。若读取也拒绝，用户无法删减；若自动截断，会隐藏实际配置并改变任务输入。只对新写入和新任务实施明确校验。

**问题 3：为什么新任务创建前还要校验？**

回答：降低 PUT 限制不会清理已有绑定。创建期校验阻止超限旧配置进入 task/event/dispatch 链路，避免异步执行后才返回笼统检索失败。

**问题 4：这会影响已有任务的幂等重试吗？**

回答：已存在 task 的同 key、同输入复用仍返回原任务；新创建才解析当前配置。已持久化 snapshot 保持原样，本片不重新调度或修改历史任务。

**问题 5：受控边界测试能代替真实 provider 回归吗？**

回答：不能。本片以受控测试验证拒绝时机、无副作用和浏览器修复；另以新任务 `2098011391776641026` 完成真实主路径 23/23 存储检查。两类证据分别回答数量边界是否一致、固定单知识库主路径是否仍能运行，均不证明大规模多知识库质量或统计可靠性。
